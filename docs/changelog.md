# Changelog и release notes

## Идея

Каждая задача пишет **свой фрагмент** в `changelog.d/<ID>.md`, а не правит `CHANGELOG.md`. Так параллельные ветки не конфликтуют. При выпуске версии `scripts/internal/release_notes.sh` собирает фрагменты в раздел версии `CHANGELOG.md` и отдельный файл release notes для неё, а фрагменты удаляет.

У записей два адресата:

| Раздел фрагмента | Для кого | Куда попадает |
|---|---|---|
| `## Для пользовательницы` | Супруга, простыми словами | `docs/release-notes/<версия>.md` (готовый текст сообщения ей: «что нового в приложении») и `CHANGELOG.md` |
| `## Для разработки` | Мы и будущие треды | Только `CHANGELOG.md` |

## Формат фрагмента

Шаблон — [changelog.d/_template.md](../changelog.d/_template.md).

```markdown
---
task: T07
type: added
---

## Для пользовательницы

- Можно плести по фото страницы из книги: полоска-линейка подсвечивает текущий ряд и запоминает место.

## Для разработки

- Таблица `image_patterns`, миграция БД v2 → v3.
- Новая зависимость `pdfrx`; разрешение камеры в Info.plist.
```

- `task` — ID задачи, совпадает с именем файла.
- `type` — один из `added` (новое), `changed` (поведение изменилось), `fixed` (исправление), `removed` (убрали), `internal` (ей не видно: каркас, рефакторинг, инфраструктура).
- Для любого `type`, кроме `internal`, раздел «Для пользовательницы» обязателен. Для `internal` его нет.
- Один фрагмент — один `type`; если задача и добавляет, и исправляет, берём главный. Исправление уже влитой задачи — новая задача со своим ID (например, `T07a`) и своим фрагментом `T07a.md`.

## Как писать строки

**Для пользовательницы:**
- Одна строка — одна возможность, начинается с того, что она может сделать или увидит.
- Без названий классов, таблиц, пакетов, английских терминов. Не «добавлен RulerCubit», а «линейка запоминает место».
- Тепло и коротко, до ~120 символов.

**Для разработки** обязательно упоминаем, если есть:
- миграцию БД (с какой на какую версию схемы);
- изменение формата `.biser` или `GridCodec`;
- новые зависимости и разрешения iOS/macOS;
- ломающие изменения интерфейсов, на которые опираются другие задачи.

## Проверки

- `scripts/internal/release_notes.sh --check` входит в `scripts/internal/check.sh`: проверяет `type`, совпадение `task` с именем файла, наличие записей и раздела для пользовательницы у не-`internal`.
- Ревьюер проверяет смысл строк по разделу `changelog` в [review/checklist.md](review/checklist.md). Нет фрагмента — замечание `major`.

## Версии и выпуск

- SemVer, до первого «настоящего» релиза — `0.x`. Вехи: M1 → `0.1.0`, M2 → `0.2.0`, M3 → `0.3.0`, M5 «Вышивка» → `0.4.0` (идёт раньше M4), M4 → `0.5.0`; промежуточные сборки — патч-версии (`0.1.1`).
- Номер сборки (`+N` в `pubspec.yaml`) растёт с каждой собранной для неё сборки.
- Выпуск (делает менеджер или тред выпуска). Релизы собираются **только из `main`**:
  1. Ветка `release/0.1.0` от свежего `dev`.
  2. `scripts/internal/release_notes.sh 0.1.0` — обновит `CHANGELOG.md`, создаст `docs/release-notes/0.1.0.md`, удалит фрагменты.
  3. Поднять `version:` в `pubspec.yaml`.
  4. PR `release/0.1.0` → `main` (merge commit, не squash). Claude только предлагает его: аппрув и мёрж делает Дмитрий. После мёржа — тег `v0.1.0` на коммит в `main` (Дмитрий или GitHub Release при мёрже) и PR `main` → `dev`, чтобы `dev` получил собранный `CHANGELOG.md`; этот PR Claude может влить сам.
  5. Сборки — из тега в `main` по [release.md](release.md): `.ipa` (Ad Hoc) для iPhone и подписанный Developer ID и нотаризованный `.app`/`.dmg` для Mac. Текст из `docs/release-notes/0.1.0.md` Дмитрий передаёт ей вместе со сборкой.
