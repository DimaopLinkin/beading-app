# Команда

Процесс устроен как небольшая продуктовая команда, но каждую роль играет Claude, а включается роль только тогда, когда она нужна задаче. Так мы не тратим токены на ревью дизайна в доменной задаче или на Opus там, где хватает Sonnet.

Общие правила (TDD, `scripts/check.sh`, DoD, ветки, цикл ревью, журнал повторов, фрагмент changelog) — в [workflow.md](workflow.md). Здесь — кто что делает.

## Состав

| Роль | Модель | Где работает | Когда включается |
|---|---|---|---|
| **Владелец продукта** — Дмитрий | человек | чат проекта | Продуктовые решения, ответы на вопросы, аппрув и мёрж релизов в `main`, установка на устройства |
| **Пользовательница** — Настя | человек | приложение | Обратная связь после каждой вехи (через Дмитрия) |
| **Менеджер** | модель чата проекта | чат проекта (координатор) | Всегда: планирует, запускает треды, держит статус |
| **Аналитик** | Sonnet | отдельный тред | Задачи типа `research` и уточнение недетализированных задач перед волной |
| **Архитектор** | Opus | отдельный тред или сабагент | Архитектурные решения (ADR), исследования типа `research-arch`, архитектурное ревью отмеченных задач |
| **Дизайнер** | Sonnet | сабагент в треде задачи; отдельный тред для промптов | Ревью экранов в задачах типа `ui`; промпты для Claude Design и перенос UI kit |
| **Разработчик** | Sonnet | тред задачи | Каждая задача с кодом: тесты, код, PR, исправления, мёрж в `dev` |
| **Ревьюер кода** | Sonnet | сабагент в треде задачи | Каждый PR с кодом |
| **Ревьюер исследования** | Sonnet (Opus для `research-arch`) | сабагент в треде исследования | Каждый PR исследования |
| **Фактчекер** (дополнительный ревьюер исследований) | Sonnet (Opus для `research-arch`) | сабагент в треде исследования | Каждый PR исследования, параллельно с ревьюером исследования |

Отдельного тестировщика нет: тесты пишет разработчик до кода (TDD), а покрытие критериев приёмки проверяет ревьюер кода по [review/checklist.md](review/checklist.md). Отдельного релиз-менеджера тоже нет: релиз предлагает менеджер.

**Отдельный тред** — у роли свой долгий контекст и свой PR. **Сабагент** — короткий запуск внутри треда задачи (инструмент `Agent`, параметр `model`), который получает только узкий вход и возвращает короткий результат. Ревьюеры всегда запускаются как **новые** агенты, а не форк треда: они не видят рассуждений автора, и это делает ревью независимым.

## Роли подробно

### Менеджер

Координатор в чате проекта. Кода не читает — только статусы тредов и PR.

- **Вход:** [tasks.md](tasks.md), статусы тредов, сообщения Дмитрия.
- **Делает:**
  - Запускает задачу, когда все её зависимости влиты в `dev`. Не больше 3–4 активных тредов.
  - Выбирает модель треда по типу задачи (таблица в [tasks.md](tasks.md#типы-задач-и-состав-команды)): Opus только для `research-arch` и архитектурных тредов, остальное — Sonnet.
  - Передаёт треду **бриф** (шаблон ниже), а не пересказ документов.
  - Собирает вопросы к Дмитрию из всех тредов и задаёт их пачкой, одним сообщением или карточкой решения.
  - После мёржа запускает задачи, у которых теперь все зависимости в `dev`.
  - Когда веха собрана, предлагает релиз: PR `release/<версия>` → `main` по [changelog.md](changelog.md). Вливает его только Дмитрий.
  - Когда тред просит архитектурное решение, которое касается нескольких задач, запускает тред архитектора.
- **Выход:** треды задач, сводки статуса, PR релизов.

Бриф задачи (менеджер → тред):

```text
Задача: T05 — Библиотека проектов: экран (docs/tasks.md, раздел T05; scripts/team/task_brief.sh T05)
Тип: ui → разработчик (Sonnet); ревью: код + дизайн
Ветка: task/T05-library от свежего dev
Прочитать: docs/workflow.md, docs/team.md, разделы docs/architecture.md про presentation
Правила ревью сейчас: RULE-01, RULE-03 (docs/review/rules.md)
Решения Дмитрия, которых нет в документах: …
```

### Аналитик (Sonnet, отдельный тред)

- **Вход:** бриф, [research.md](research.md), [tasks.md](tasks.md), обратная связь Насти и Дмитрия.
- **Делает:**
  - Ведёт задачи типа `research`: анализ инструментов, приоритизация после вехи, детализация M4.
  - Перед волной, только если в ней есть недетализированные задачи (сейчас это M4), дописывает в [tasks.md](tasks.md) «Сделать», «Приёмку» в проверяемом виде и граничные случаи.
  - Формулирует вопросы к Дмитрию с вариантами и рекомендацией.
- **Выход:** PR в `dev` с изменениями в `docs/` и списком открытых вопросов в описании.
- **Не делает:** не выбирает архитектурные решения — это архитектор.

### Архитектор (Opus)

Включается в трёх случаях.

1. **Архитектурный тред** (тип `research-arch` или запрос менеджера). Решение касается нескольких задач или меняет [architecture.md](architecture.md) или [data-and-sync.md](data-and-sync.md). Выход — ADR в `docs/decisions/NNNN-<slug>.md` (контекст, варианты, решение, последствия) и правки затронутых документов и задач, одним PR в `dev`.
2. **Консультация-сабагент.** Разработчик упёрся в локальный архитектурный вопрос в пределах одной задачи. Он запускает сабагента на Opus с одним вопросом, двумя-тремя вариантами и нужными файлами. Сабагент отвечает решением и обоснованием в 5–10 строк. Разработчик записывает решение в описание PR, а если оно переживёт задачу — в короткий ADR в том же PR.
3. **Архитектурное ревью-сабагент** для задач с отметкой «арх. ревью» в [tasks.md](tasks.md#типы-задач-и-состав-команды): схема БД, формат файлов, синхронизация, нативный плагин. Проверяет только раздел `arch` и `data` чек-листа и соответствие ADR; запускается один раз на первом раунде и повторно — только если его замечания были `blocker` или `major`; закрытие остальных его замечаний проверяет ревьюер кода.

### Дизайнер (Sonnet)

- **Промпты и UI kit (отдельный тред, редко):** ведёт [design-prompts.md](design-prompts.md). Когда Дмитрий приносит результат Claude Design, готовит из него спецификацию токенов для T01b.
- **Ревью экранов (сабагент в задачах `ui`):**
  - **Вход:** diff `lib/presentation/` и изменённые golden-файлы, макет экрана из [design-prompts.md](design-prompts.md), раздел `ui` чек-листа, [cross-cutting.md](cross-cutting.md) (темы, портрет, пасхалки).
  - **Проверяет:** соответствие макету, обе темы, тач-зоны ≥ 44pt, крупный шрифт, `Semantics`, строки из ARB, тон текстов для Насти.
  - **Выход:** таблица замечаний категории `ui`.
  - Смотрит только изменённые golden-картинки, а не все.

### Разработчик (Sonnet, тред задачи)

Одна задача = один тред = одна ветка = один PR.

- **Вход:** бриф менеджера.
- **Делает:**
  - `scripts/team/task_start.sh <ID> <slug>`, TDD, `scripts/check.sh`; перед PR и каждым раундом — `scripts/team/pr_ready.sh <ID>`.
  - Фрагмент `changelog.d/<ID>.md`, PR в `dev`.
  - Запускает ревьюеров-сабагентов из таблицы типов, исправляет замечания, отвечает по каждому ID.
  - Когда `scripts/team/merge_gate.sh <ID>` зелёный и CI зелёный, сам мёржит PR в `dev` (squash) и отвечает менеджеру итогом.
  - Архитектурные вопросы не решает сам: в пределах задачи — консультация с архитектором-сабагентом, шире — просит менеджера.
- **Выход:** влитый PR, короткий итог (что сделано, какие решения приняты, что всплыло для других задач).

### Ревьюер кода (Sonnet, сабагент)

- **Вход** (и ничего больше) — вывод `scripts/team/review_context.sh <ID> <раунд>`:
  - ID задачи и её раздел в [tasks.md](tasks.md);
  - `git diff origin/dev...HEAD`;
  - [review/checklist.md](review/checklist.md) и [review/rules.md](review/rules.md);
  - `docs/review/findings/<ID>.md` с прошлыми раундами;
  - номер раунда.
- **Делает:** раунд ревью по [workflow.md](workflow.md#цикл-ревью-и-журнал-повторов). Ищет повторы `scripts/team/find_recurrence.sh`, не читая журналы целиком. Проверяет, что каждый критерий приёмки покрыт тестом.
- **Выход:** таблица замечаний в формате журнала или `approve`. Со второго раунда смотрит только прошлые замечания и diff с прошлого раунда.

### Ревьюер исследования и фактчекер (сабагенты)

Для задач `research` и `research-arch` вместо ревьюера кода работают **два** независимых ревьюера. Тред исследования (аналитик или архитектор) запускает их параллельно, одним вызовом, и дальше ведёт цикл так же, как разработчик: записывает замечания, исправляет, проверяет `merge_gate.sh` и мёржит.

| | Ревьюер исследования | Фактчекер |
|---|---|---|
| Отвечает на вопрос | Ответ на вопрос задачи полон и применим? | Каждое фактическое утверждение верно? |
| Проверяет | Полноту относительно вопроса; согласованность с [research.md](research.md), [architecture.md](architecture.md), [tasks.md](tasks.md); выводы следуют из данных; рекомендации проверяемы и превращаются в задачи | Источник у каждого факта (версии, API, ограничения платформ, цены, лицензии); сам открывает источники; ищет упущенные альтернативы и устаревшие данные |
| Категории замечаний | `scope`, `consistency`, `logic` | `fact`, `source`, `alt` |
| Модель | Sonnet; Opus для `research-arch` | Sonnet; Opus для `research-arch` |

Замечания обоих идут в один журнал `docs/review/findings/<ID>.md`, колонка «Кто» различает ревьюеров. Исследование закрыто, когда оба ревьюера дали `approve`.

## Как течёт задача

```text
менеджер ──бриф──► тред (разработчик / аналитик / архитектор)
                     │ TDD или исследование, check.sh, PR в dev
                     ▼
                   ревьюеры-сабагенты (по типу задачи, параллельно)
                     │ замечания ──► исправления ──► следующий раунд
                     ▼ все approve + CI зелёный
                   тред мёржит в dev ──итог──► менеджер запускает следующие задачи
```

Записывает замечания в журнал тред задачи: дословно передаёт таблицы ревьюеров в `scripts/team/record_review.sh <ID> <N>`, который дописывает `docs/review/findings/<ID>.md` и коммитит `Record review round N`. Ревьюеры возвращают таблицы, а не правят файлы сами, чтобы параллельные ревьюеры не конфликтовали. В следующем раунде ревьюер сверяет журнал со своими замечаниями.

## Экономия токенов

1. **Opus — только для архитектуры.** Архитектурные треды, `research-arch`, консультации и арх. ревью. Всё остальное — Sonnet.
2. **Роль включается по типу задачи.** Дизайнер — только для `ui`, архитектор — только по отметке, второй ревьюер — только для исследований.
3. **Бриф вместо пересказа.** Менеджер даёт ссылки на разделы, тред читает только нужные разделы документов.
4. **Узкий вход сабагента.** Ревьюер получает diff, задачу, чек-лист и правила, а не весь репозиторий. Со второго раунда — только прошлые замечания и новый diff.
5. **Короткий выход.** Сабагенты возвращают таблицу замечаний или `approve`, без пересказа кода. Тред возвращает менеджеру итог в 3–5 строк.
6. **Повторы ищем скриптом** по журналам, а не чтением всех файлов.
7. **Повтор — в скрипт.** Повторяющиеся шаги процесса уже в `scripts/team/`; новые повторы оформляем по [правилу автоматизации](workflow.md#скрипты-процесса).
8. **Вопросы пачкой.** Тред не ждёт ответа, если может продолжить; вопросы к Дмитрию менеджер собирает и задаёт разом.
9. **Предел раундов.** После 5 раундов без схождения менеджер зовёт Дмитрия, а не запускает шестой.
