# ADR-0006. Синхронизация устройств через Supabase вместо iCloud/CloudKit

- **Статус:** принято (архитектурное ревью R-01…R-16 пройдено, 2026-11-12)
- **Дата:** 2026-11-12
- **Задача:** A03 (вместо плана с CloudKit в T27); детализирует T26–T28

## Контекст

Автосинк между iPhone и MacBook был запланирован через CloudKit (`CKSyncEngine`, Swift-плагин, [data-and-sync.md](../data-and-sync.md)). 2026-11-12 Дмитрий отказался от iCloud: у него есть Supabase, нужен realtime. Требования: у каждого пользователя доступны только его данные (учётная запись), вход только по почте и паролю (Apple ID и портал разработчика не нужны), приложение полностью работает без входа и без сети.

Остаётся в силе: локальная база drift с полями `id`, `updated_at`, `deleted_at`, `device_id`, правила слияния из data-and-sync.md, интерфейс `SyncRemote` в домене. Сборки ставятся вручную, поэтому на двух устройствах днями будут **разные версии приложения** (учтено в R-13).

## Рассмотренные варианты

1. **Таблица Supabase на каждую таблицу drift.** Любое изменение схемы drift требует миграции на сервере и порядка обновления устройств. Отклонено.
2. **Одна таблица `sync_records` с `jsonb`-нагрузкой + Storage для файлов.** Схема сервера стабильна, одна политика RLS, слияние в Dart под тестами. Типизация живёт в мапперах Dart. **Выбрано.**
3. **Готовые движки (PowerSync, ElectricSQL).** Своя модель слияния не знает наших правил; избыточно для двух устройств. Отклонено.
4. **Остаться на iCloud.** Отклонено решением Дмитрия.

## Решение

### Слои

- `domain/sync/`: `SyncRecord`, `MergePolicy` (чистые функции, 100% покрытие), `SyncRemote` (интерфейс: `push` с ответом «принято/отклонено» по каждой записи, `pullSince`, `wake`-поток), `SyncEngine`. Ничего не знают о Supabase и drift.
- `data/sync/`: `DriftSyncStore` (чтение outbox, мапперы строка ↔ `SyncRecord`, применение), `SupabaseSyncRemote`, `SupabaseAuthRepository` (интерфейс `AuthRepository` в домене).
- `presentation/settings/`: раздел «Синхронизация» (вход, выход, статус, «Синхронизировать сейчас»), нативные виджеты (ADR-0001).

### Аккаунт и безопасность

- Supabase Auth, только email + пароль. **Регистрация выключена с самого начала** («Allow new users to sign up» off); обе учётные записи (Дмитрий и Настя) создаёт Дмитрий в дашборде (Authentication → Users → Add user, с автоподтверждением). Встроенная почта Supabase шлёт письма только участникам организации, поэтому в приложении **нет** экрана регистрации и «забыли пароль» (пароль сбрасывает Дмитрий в дашборде). Минимальная длина пароля задаётся в настройках Auth.
- Сессия: свой `LocalStorage` для `supabase_flutter` на `flutter_secure_storage` (по умолчанию SharedPreferences не годится). iOS: Keychain, Ad Hoc без особых прав. macOS: `MacOsOptions(useDataProtectionKeyChain: false)` (обычный login keychain, работает с Developer ID без provisioning profile; `keychain-access-groups` не нужны). Debug-сборки Mac с подписью «-» допускают файл 0600 в Application Support (keychain иначе спрашивает пароль на каждую сборку). Пароль не хранится никогда, только refresh-токен.
- В приложении только публичный ключ, через `--dart-define` (в репозиторий не попадает). `service_role` в приложении и репозитории не используется.
- RLS на всех таблицах и в бакете; `anon` без каких-либо прав на `sync_records` и `blobs` (`revoke all … from anon`). `user_id` ссылается на `auth.users on delete cascade`.
- Без сквозного шифрования; данные у провайдера шифруются на диске. Для рукодельных схем принято.

### Серверная схема (миграции в `supabase/migrations/`, применяются после повторного просмотра)

```sql
create sequence public.sync_seq;

create table public.sync_records (
  user_id    uuid   not null references auth.users on delete cascade,
  entity     text   not null,
  sync_id    text   not null,          -- см. таблицу ключей
  updated_at bigint not null,          -- UTC ms, монотонный на запись (R-04)
  deleted_at bigint,
  device_id  text   not null,
  data       jsonb  not null,          -- у надгробия '{}'
  server_seq bigint not null default 0,-- ставит триггер
  primary key (user_id, entity, sync_id)
);
create index on public.sync_records (user_id, server_seq);
```

**Запись через обычный upsert PostgREST, LWW держит сервер** (R-03): триггер `BEFORE INSERT OR UPDATE`, `security invoker`, `set search_path = ''`:
1. `perform pg_advisory_xact_lock(hashtextextended(auth.uid()::text, 0))`: записи одного пользователя сериализуются, `server_seq` выдаются и коммитятся в одном порядке, снимок читателя всегда видит префикс (R-02; иначе курсор пропускал бы записи: транзакция с меньшим seq коммитится позже).
2. `new.user_id := auth.uid()` (чужой `user_id` из payload игнорируется), `new.server_seq := nextval('public.sync_seq')`.
3. Серверный клампинг: `new.updated_at := least(new.updated_at, now_ms + 5 мин)`; видят его все устройства.
4. В ветке UPDATE: если `(new.updated_at, new.device_id) <= (old.updated_at, old.device_id)`, `return null` (устаревшая запись молча пропускается, повтор безопасен).

Политики: `select using (user_id = (select auth.uid()))`; `insert`/`update with check (user_id = (select auth.uid()))`; `delete` клиенту не нужен и не выдаётся. Колонка `server_seq` обычная `bigint` (в `generated always as identity` нельзя писать при UPDATE).

Замечания к реализации: PostgREST-upsert (`INSERT … ON CONFLICT DO UPDATE`) запускает оба триггера, `nextval` берётся дважды (пропуски в seq допустимы, важен порядок); контрактный тест проверяет, что `return null` в ветке UPDATE оставляет старую строку и старый `server_seq`; нужен `grant usage on sequence public.sync_seq to authenticated`.

Ответ push: после upsert клиент делает `select` по принятым ключам и сверяет `server_seq`/`updated_at`: что осталось старым, помечено «отклонено» (нужно для будущего трёхстороннего слияния без смены протокола, R-09).

**Realtime (R-14).** Выбран `postgres_changes` на `sync_records` с фильтром `user_id=eq.<uid>` (проще, для двух пользователей строка целиком терпима); событие **только будит pull**, содержимое не применяется. Pull также при каждом переходе канала в `SUBSCRIBED` (события за время разрыва потеряны). Если нагрузка вырастет, заменяем на Broadcast из триггера (пустая нагрузка, приватный топик `user:<uid>`), без смены протокола.

**Storage.** Приватный бакет `blobs`, путь `{user_id}/{entity}/{sync_id}/{хеш}`; политики: select и insert по первой папке, **без update** (объекты неизменяемые), delete только своих. **Правило по полю, а не по размеру** (R-08): всегда в Storage (gzip для `cells`/`layers`): `cells`, `layers`, файлы страниц схем и PDF, обложки; всегда inline base64 в `data`: биты блоков клеток, ряды, `markup` страниц (его размер проверить при реализации T27′). Хранение BLOB в `bytea` отклонено: 500 МБ базы общие, pull порциями с мегабайтными строками тяжёл.
- Загрузка пропускается, если хеш не изменился (иначе каждое «остановилась здесь» перекачивало бы сетку); страницы книг пережимаются (JPEG/HEIC, ограничение длинной стороны) до загрузки.
- При приёме: сначала скачать файл и проверить хеш, потом применять запись. Не скачался — запись не применяется, курсор не двигается дальше неё (повтор в следующем цикле).
- Занятое место показывается в статусе; переключатель «синхронизировать страницы книг» (квота 1 ГБ: книги и PDF главный риск).
- Файлы удаляются **только через Storage API** (SQL-удаление оставляет сирот): клиент после подтверждённого push надгробия или смены хеша удаляет старый объект; редких сирот чистит служебная кнопка в приложении, сверяющая объекты со ссылками.

### Ключи слияния (`sync_id`) по сущностям (R-05)

Слияние сводит записи по `sync_id`, а не по локальному `id`, иначе два устройства, офлайн отметившие ряд 5, дадут две записи и упадут на unique-ограничении drift.

| Сущность | `sync_id` | Комментарий |
|---|---|---|
| `projects` | `id` проекта (UUID v7) | |
| `grid_patterns` | `project_id` | 1:1 с проектом; палитра (`pattern_colors`) внутри `data`, отдельно не синхронизируется |
| `grid_cursor` | `project_id` | `current_row`/`current_bead` вынесены из `grid_patterns` (R-09): LWW отдельно, не переотправляет сетку при каждом продвижении. В drift остаются колонками, разделяет их маппер `DriftSyncStore` |
| `image_patterns` | `project_id` | 1:1 |
| `image_pattern_pages` | `{project_id}:{position}` | |
| `grid_progress_rows` | `{project_id}:{row_index}` | множество, снятие отметки надгробием |
| `grid_progress_cells` | `{project_id}:{block_index}` | LWW блока (R-09) |
| `work_sessions` | `id` | |
| `floss_stock` | `{brand}:{code}` | в drift добавляется unique «одна живая запись на нитку»; два офлайн-добавления сливаются как LWW количества, принято |
| `bead_stock` | `{brand}:{code}` | запас бисера в граммах, как `floss_stock` (добавлено в схеме v16) |
| `settings` | `key` (без `local.*`) | |

Ссылки детей в `data` указывают на **`sync_id` родителя**, а не на локальный id; `DriftSyncStore` переводит их обратно. Чтобы переводов не было, локальные id 1:1-детей (`grid_patterns`, `image_patterns`) миграцией делаются детерминированными (UUID v5 от `project_id`). Какой из двух приёмов выбран, фиксируется в T26 после проверки миграции на существующих данных.

### Формат записи и версии приложения (R-13, блокер)

- В каждой записи `data.v` — версия формата сущности (кодеки `cells_codec_version`/`layers_codec_version` лежат внутри).
- Клиент, у которого `v` записи выше поддерживаемой, **не применяет и не перезаписывает её**, показывает «обновите приложение на этом устройстве».
- После обновления приложения, если выросла поддерживаемая версия любой сущности, `pull_cursor` сбрасывается в 0 (полный pull, при наших объёмах дёшево): пропущенные записи иначе не вернулись бы.
- Менять формат можно только совместимо (новое поле со значением по умолчанию); переименование и смена смысла — новая `v`. Мапперы обязаны сохранять неизвестные поля записи без потерь при обратной записи той же `v`. Для этого хранится локальная «теневая» таблица `sync_shadow(entity, sync_id, data)` с последней принятой нагрузкой; при push маппер накладывает известные поля поверх неё (в drift-строке неизвестным полям места нет). Тест: запись новой `v` пропускается старым клиентом, курсор идёт дальше, после «обновления» полный pull её применяет.

### Алгоритм

1. **Очередь изменений (R-01).** Локальная таблица `sync_outbox(entity, sync_id)` (PK по паре, повторная правка не плодит строк), которую заполняют **SQLite-триггеры** `AFTER INSERT/UPDATE` на каждой синхронизируемой таблице (ловят и будущие пути записи). На время применения входящих записей триггеры глушатся флагом (строка во временной таблице `sync_applying`, проверяется в `WHEN`). После подтверждения сервера удаляются ровно те пары, чья строка не менялась после чтения (сравнение `updated_at`). Миграция drift с тестом по правилам data-and-sync.md. Часы устройства больше не влияют на то, что уйдёт на сервер.
2. **`sync_state`** (локальная): `user_id`, `pull_cursor` (последний принятый `server_seq`). Курсор двигается только после успешного применения порции.
3. **Цикл:** `pull` до конца (порции по 500, **все порции во временную область**) → слияние в Dart → одна транзакция применения → `push` из outbox порциями.
4. **Применение и внешние ключи (R-06).** В drift `PRAGMA foreign_keys = ON`. Применяется одной транзакцией в порядке «родители → дети» (`projects` → `image_patterns`/`grid_patterns` → страницы, ряды, клетки, сессии, `grid_cursor`) и с `PRAGMA defer_foreign_keys = ON`; порядок `server_seq` не гарантирует иерархию. Правило **«удаление поддерева побеждает»** делается фильтром при применении: ребёнок, чей родитель в надгробии, не применяется живым и не показывается, даже если его запись новее надгробия родителя; надгробие ребёнку не пишется, чтобы при оживлении родителя («сброс схемы», отмена удаления) дети не были уничтожены безвозвратно. Каскадное надгробие проекта поднимает `updated_at` детей; push большой схемы (≈1900 блоков клеток для 200×80 см) проверяется тестом на размер и время.
5. **Слияние** (`MergePolicy`): запись целиком — LWW по `(updated_at, device_id)`; `grid_patterns` с палитрой как одна единица; `grid_progress_rows` — множество; `grid_progress_cells` — LWW блока 16×16 целиком (ADR-0003). Потеря отметок при одновременной вышивке одного блока на двух офлайн-устройствах принимается и документируется; OR битов не берётся (сделал бы снятие отметки невозможным). Если потеря проявится, путь — трёхстороннее слияние битов с хранением базовой версии блока и условной записью по `server_seq`; протокол к этому готов (push возвращает «принято/отклонено»).
6. **Монотонный `updated_at` на запись (R-04).** При правке существующей записи репозитории ставят `updated_at = max(clock.now, old.updated_at + 1)`: правка поверх версии всегда новее этой версии, независимо от часов. Клиентского клампинга нет; от устройства с часами в 2030 году защищает серверный клампинг в триггере.
7. **Запуски цикла:** вход; старт; возврат из фона; через 3 секунды после последней правки; событие realtime и переход канала в `SUBSCRIBED`; кнопка. Нет сети: тихо ждём, повтор с нарастающей паузой.
8. **Смена пользователя.** `sync_state.user_id` хранит владельца данных. Другой аккаунт на этом устройстве: синхронизация не стартует, пока пользователь не выберет «привязать локальные данные к новому аккаунту» или «сначала резервная копия и очистка». Молчаливого смешения нет.
9. **Первый вход:** локально есть, на сервере пусто — загрузка всего; есть и там и там — обычное слияние, ничего не удаляется.
10. **Восстановление копии и импорт `.biser` при включённой синхронизации (R-15).** Восстановление = правки с новыми `updated_at` (через репозитории) плюс надгробия для того, чего в копии нет; иначе сервер по LWW молча «отменил» бы восстановление. Правило выносится в T28 и в тест. Резервная копия всей базы остаётся отдельным файлом: сервер её не заменяет.
11. **Удаление (R-07).** Надгробия на сервере хранятся **бессрочно**, `data = '{}'`, файлы Storage удаляются (~200 байт на надгробие, единицы МБ из 500 даже при десятках тысяч). `pg_cron` не нужен, раздел про 90 дней и правку data-and-sync.md (30 дней) снимаются. Локальные надгробия чистятся только те, что уже на сервере (outbox пуст), либо не чистятся.

### Что не делаем

Совместное редактирование между аккаунтами, общий доступ к проектам, сквозное шифрование, вход через Apple/Google, анонимные пользователи, публичные ссылки на файлы, регистрацию и сброс пароля в приложении.

## Последствия

- **Пауза свободного проекта (R-10).** Проект после недели низкой активности ставится на паузу, и вернуть его можно только кнопкой **Resume project** в дашборде (в течение 90 дней): неделя без вышивки означает, что синхронизация лежит, пока Дмитрий не зайдёт в дашборд (Supabase присылает письмо за неделю до паузы). Приложение различает «нет сети» и «сервер недоступен долго» и показывает понятный статус; данные локально целы. Решение о keep-alive (плановый запрос раз в день из GitHub Actions с публичным ключом к пустой RPC) за Дмитрием. На свободном тарифе нет резервных копий: **сервер не заменяет локальную резервную копию в файл**.
- Ограничения тарифа: 500 МБ база, 1 ГБ хранилище; страницы PDF и книг в бакете — главный расход (см. Storage).
- iCloud-часть плана снимается: Swift-плагин, права `com.apple.developer.icloud-*`, деплой схемы CloudKit. В docs/release.md CloudKit-шаги помечаются устаревшими; bundle ID остаётся `com.dimaoplinkin.beading`.
- Для macOS нужен `com.apple.security.network.client` (Debug и Release). Нативный код не нужен: `supabase_flutter` на Dart. Новые зависимости: `supabase_flutter`, `flutter_secure_storage`.
- Тесты `SyncEngine`/`MergePolicy` на фейковом `SyncRemote` с двумя «устройствами»: обрыв сети посреди пакета, повторная отправка, **ребёнок раньше родителя (в первой порции ребёнок, во второй родитель)**, часы назад, новая версия формата на старом клиенте, удаление проекта против офлайн-правки ребёнка, восстановление копии, смена пользователя.
- Контрактные тесты `SupabaseSyncRemote` и RLS на локальном стеке Supabase (CLI), не на рабочем проекте: две параллельные транзакции, одна держит коммит (R-02); чужой `user_id` отвергается и устаревшая запись не затирает новую (R-03); `anon` без доступа к таблице и бакету.
- Нарезка: **T26** (доменное слияние, фейковый remote, тесты, outbox-миграция drift, монотонный `updated_at`, `sync_id`-мапперы), **T27′** (миграции Supabase, `SupabaseSyncRemote`, Storage), **T28** (вход, статус, `sync_state`, правило восстановления). Серверная схема применяется к проекту `kanitel` только в T27′ после повторного просмотра.

## Решения Дмитрия (2026-11-12)

1. **Keep-alive от паузы:** делаем через GitHub Actions (бесплатно для публичного репозитория): workflow раз в день шлёт запрос с публичным ключом к пустой RPC `keep_alive`. URL и публичный ключ лежат в секретах репозитория, не в коде. Оговорка GitHub: плановые workflow в публичном репозитории отключаются после 60 дней без активности в репозитории, пока идёт разработка это не проблема, позже достаточно включить заново. Реализация в T27′: функция `public.keep_alive()` (доступна `anon`, ничего не читает и не пишет, отдельно от таблиц), workflow по cron раз в день с секретами `SUPABASE_URL` и `SUPABASE_PUBLISHABLE_KEY`. Workflow не падает громко, пока проект на паузе (ожидаемо), но становится красным при любой другой ошибке, чтобы пришло письмо GitHub.
