# ADR-0006. Синхронизация устройств через Supabase вместо iCloud/CloudKit

- **Статус:** предложено (ждёт архитектурного ревью, код не пишется)
- **Дата:** 2026-11-12
- **Задача:** A03 (вместо плана с CloudKit в T27); детализирует T26–T28

## Контекст

Автосинк между iPhone и MacBook был запланирован через CloudKit (`CKSyncEngine`, Swift-плагин, [data-and-sync.md](../data-and-sync.md)). 2026-11-12 Дмитрий отказался от iCloud: у него есть Supabase, нужен realtime. Требования: у каждого пользователя доступны только его данные (учётная запись), вход только по почте и паролю (Apple ID и работа в портале разработчика не нужны), приложение остаётся полностью рабочим без входа и без сети, сборки Ad Hoc и Developer ID больше не отличаются средой, как было у CloudKit.

Готово и сохраняется: локальная база drift с полями `id`, `updated_at`, `deleted_at`, `device_id` во всех синхронизируемых таблицах, правила слияния из data-and-sync.md (LWW запись целиком, объединение множеств, блоки 16×16, tombstones, `local.*` не синхронизируется), интерфейс `SyncRemote` в домене.

## Рассмотренные варианты

1. **Таблица Supabase на каждую таблицу drift.** Типизированно, видно в Table Editor. Минусы: любое изменение схемы drift требует миграции и в Postgres, и на уже установленных устройствах в нужном порядке; 10+ таблиц, 10+ подписок. Отклонено.
2. **Одна таблица `sync_records` с `jsonb`-нагрузкой + Storage для больших файлов.** Схема на сервере не меняется при изменениях в приложении, одна политика RLS, один канал realtime. Слияние остаётся в Dart (там оно покрыто тестами), сервер только хранит и отфильтровывает устаревшее. **Выбрано.**
3. **Готовые движки (PowerSync, ElectricSQL, Supabase Realtime как источник правды).** Решают офлайн, но добавляют сервис или чужую модель слияния, не знающую про наши правила (ряды как множество, схема и палитра как одна единица). Для двух устройств одного человека избыточно. Отклонено.
4. **Остаться на iCloud.** Отклонено решением Дмитрия.

## Решение

### Слои

- `domain/sync/`: `SyncRecord` (сущность, id, натуральный ключ, `updatedAt`, `deletedAt`, `deviceId`, нагрузка), `MergePolicy` (чистые функции, 100% покрытие), `SyncRemote` (интерфейс: `push`, `pullSince`, `changes`), `SyncEngine` (оркестрация: что отправить, что принять). Ничего не знают о Supabase и drift.
- `data/sync/`: `DriftSyncStore` (чтение изменённых записей, применение слитых в одной транзакции, мапперы строка ↔ `SyncRecord`), `SupabaseSyncRemote`, `SupabaseAuthRepository` (интерфейс `AuthRepository` в домене).
- `presentation/settings/`: раздел «Синхронизация»: вход, выход, статус, «Синхронизировать сейчас». Нативные Cupertino-виджеты (ADR-0001).

### Аккаунт и безопасность

- Supabase Auth, только email + пароль. Сессия хранится в Keychain (`flutter_secure_storage`); на macOS с подписью «-» Keychain может не работать, запасной вариант — файл в Application Support с правами 0600 (проверяется на Mac при приёмке).
- Регистрация выключается в настройках проекта после создания двух учётных записей (Дмитрий и Настя): иначе любой с ключом может создать аккаунт. Подтверждение почты включено.
- В приложении только публичный ключ (publishable/anon), он не секрет, но в репозиторий не попадает: URL и ключ приходят через `--dart-define` (`scripts/` читают их из окружения). Секретный `service_role` ключ в приложении и в репозитории не используется никогда.
- RLS включена на всех таблицах и бакетах: `user_id = (select auth.uid())` для select/insert/update/delete. В Storage путь `{user_id}/…`, политика по первой папке.
- Данные хранятся на серверах Supabase без сквозного шифрования (шифрование на диске есть у провайдера). Для рукодельных схем принято. Если нужно сквозное, это отдельное решение.

### Серверная схема (миграции в `supabase/migrations/`, применяются только после ревью)

```sql
create table public.sync_records (
  user_id    uuid not null default auth.uid() references auth.users on delete cascade,
  entity     text not null,            -- project, grid_pattern, progress_row, ...
  id         text not null,            -- id записи (UUID v7) или натуральный ключ
  updated_at bigint not null,          -- UTC ms, как в drift
  deleted_at bigint,
  device_id  text not null,
  data       jsonb not null,
  server_seq bigint generated always as identity,  -- курсор для pull, не зависит от часов устройств
  primary key (user_id, entity, id)
);
create index on public.sync_records (user_id, server_seq);
```

- `server_seq` выдаётся сервером при каждой записи (в `sync_push` перезаписывается из `nextval` для обновлённых строк), поэтому «забрать всё после курсора» не теряет записи при расхождении часов.
- Запись только через функцию `sync_push(records jsonb)` (`security invoker`, вызывает RLS): для каждой записи `insert … on conflict do update … where (excluded.updated_at, excluded.device_id) > (sync_records.updated_at, sync_records.device_id)`. Так устаревшая запись с отставшего устройства не затирает новую, повтор отправки безопасен (идемпотентно). Прямые insert/update клиенту запрещены политиками, остаётся только select.
- Realtime: публикация `supabase_realtime` на `sync_records`, подписка `postgres_changes` с фильтром `user_id=eq.<uid>`; событие только будит `pull`, содержимое из события не применяется (одна точка слияния).
- Большие нагрузки (BLOB `cells`/`layers` сетки, страницы схем из книг и PDF, обложки) — в приватный бакет `blobs` по пути `{user_id}/{entity}/{id}-{хеш}`; в `data` лежит ссылка и хеш. Порог: всё, что больше 32 КБ. Меньшее (блоки прогресса 16×16 по 32 байта, ряды) — base64 в `data`. Загрузка файла предшествует `sync_push`, скачивание по хешу: одинаковый файл не качается повторно.

### Алгоритм

1. **Локальная пометка изменений.** В drift добавляется таблица `sync_state` (локальная, `local.*`-семантика): `user_id`, `pull_cursor` (последний принятый `server_seq`), `pushed_up_to` (максимальный `updated_at`, отправленный на сервер). Изменённая запись = `updated_at > pushed_up_to`. Новых флагов в таблицах данных нет (миграция только на одну таблицу).
2. **Цикл:** `pull` (все записи `server_seq > pull_cursor`, порциями по 500) → слияние в Dart → запись в базу одной транзакцией → `push` изменённых (порциями) → `pull_cursor` и `pushed_up_to` сдвигаются только после успеха.
3. **Когда запускается:** вход в аккаунт; старт приложения; возврат из фона; через 3 секунды после последней локальной правки (debounce); событие realtime; кнопка «Синхронизировать сейчас». Нет сети: тихо ждём, показываем «ожидает», повтор с нарастающей паузой.
4. **Слияние** (по entity, `MergePolicy`): запись целиком — LWW по `(updated_at, device_id)`; `grid_pattern` вместе с `pattern_colors` как единая запись (палитра лежит в `data` схемы); `grid_progress_rows` — множество по ключу `(grid_pattern_id, row_index)`, отметка снимается tombstone; `grid_progress_cells` — LWW по блоку (как сейчас, ADR-0003; OR по битам обсуждается на ревью); `settings` (кроме `local.*`) — LWW по ключу. Каталоги, пасхалки, `local.*` не синхронизируются.
5. **Часы.** `updated_at` ставит клиент. Входящая запись с `updated_at` больше `now + 5 мин` при слиянии принимается с `updated_at = now`, чтобы устройство с уехавшими часами не «заморозило» запись навсегда.
6. **Смена пользователя.** В `sync_state` хранится `user_id`, чьи данные в базе. Если на устройстве входит другой аккаунт, синхронизация не стартует, пока пользователь не выберет: «оставить локальные данные и привязать к новому аккаунту» или «сначала сделать резервную копию и очистить». Данные никогда не смешиваются молча.
7. **Первый вход.** Локальные данные есть, на сервере пусто: загрузка всего. Данные есть и там и там: слияние обычным путём, ничего не удаляется.
8. **Удаление.** Tombstone живёт на сервере 90 дней (вместо 30, см. ниже), затем удаляется задачей `pg_cron`. Устройство, которое не синхронизировалось дольше 90 дней, при входе делает «полный pull» и не отправляет записи старше потерянных tombstone: сначала принимает всё с сервера. Файлы бакета, на которые больше нет ссылок, чистятся той же задачей.

### Что не делаем

Совместное редактирование между аккаунтами, общий доступ к проектам, сквозное шифрование, Apple/Google вход, анонимные пользователи, публичные ссылки на файлы.

## Последствия

- Свободный тариф Supabase приостанавливает проект после недели без запросов. Для двух активных пользователей это не страшно, но после долгого перерыва первая синхронизация может ждать «пробуждения». Ограничения тарифа: 500 МБ база, 1 ГБ хранилище, хватает на сотни схем без картинок; страницы PDF в бакете могут съесть квоту, поэтому в статусе показываем занятое место. Платный план не нужен, пока это не изменится.
- Время жизни tombstone поднято до 90 дней (в data-and-sync.md было 30): устройство «в ящике» дольше месяца иначе воскресило бы удалённые записи. Документ обновляется при реализации T26.
- iCloud-часть плана снимается: Swift-плагин, права `com.apple.developer.icloud-*`, деплой схемы CloudKit в Production, различие сборок по среде CloudKit. В docs/release.md CloudKit-шаги помечаются устаревшими; bundle ID остаётся `com.dimaoplinkin.beading`.
- Нужны права `com.apple.security.network.client` для macOS (Debug и Release); для Ad Hoc iOS ничего особенного.
- Нативный код не нужен: `supabase_flutter` на Dart для iOS и macOS. Новая зависимость и ключи окружения.
- Тестируемость: `SyncEngine` и `MergePolicy` проверяются на фейковом `SyncRemote` в памяти (два «устройства», обрыв сети посреди пакета, повторная отправка, часы вперёд, tombstone, смена пользователя). Контрактные тесты `SupabaseSyncRemote` и политик RLS идут на локальном стеке Supabase (CLI) или отдельной ветке проекта, не на рабочем проекте.
- Реализация режется на PR: T26 (домен слияния + фейковый remote + тесты), T27′ (миграции Supabase, `SupabaseSyncRemote`, Storage), T28 (вход, статус в настройках, `sync_state`).

## Вопросы к архитектурному ревью

1. `sync_records` с `jsonb` против таблицы на сущность: приемлемо ли отсутствие типизации на сервере ради стабильной схемы?
2. `server_seq` как курсор и серверный LWW в `sync_push`: достаточно ли, нет ли пропусков при параллельных транзакциях (identity не монотонна по моменту фиксации)? Альтернатива: курсор по `updated_at` сервера с нахлёстом.
3. Клиентская пометка «изменено» через `updated_at > pushed_up_to`: не теряются ли записи, слитые из чужих данных (у них `updated_at` старый)? Нужна ли отдельная очередь изменений?
4. Прогресс по клеткам: оставить LWW блока или перейти на OR битов (отметки на двух устройствах не теряются, но снять отметку труднее)?
5. Порог 32 КБ и хранение BLOB в Storage против `bytea` в таблице.
6. Keychain на macOS с подписью Developer ID и в разработке: запасное хранилище сессии.
7. Отключение регистрации: делать самим или оставить включённой с подтверждением почты.
