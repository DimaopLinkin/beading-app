# ADR-0007: Внедрение зависимостей без get_it, модули фич на чистом Dart

- Статус: принято (Дмитрий согласовал 2026-11-12)
- Дата: 2026-11-12
- Задача: A14
- Заменяет пункт «DI: get_it» в [architecture.md](../architecture.md#ключевые-решения)

## Контекст

Дмитрий считает глобальный контейнер get_it антипаттерном: «море синглтонов, которые не всегда нужны во всём приложении», зависимости фич можно держать в самих фичах. Перед решением посмотрели, как get_it используется на самом деле (ветка `dev`, 2026-11-12).

### Что хорошо уже сейчас

- **Классического Service Locator нет.** `getIt` не вызывается ни в `domain`, ни в `data`, ни в `presentation`: все Cubit, use case и репозитории получают зависимости через конструктор. Вызовы есть только в `lib/app`: `di.dart` (регистрации), `router.dart` (26 мест), `app.dart` (9), `bootstrap.dart` (4).
- Тесты фич (212 файлов) собирают объекты руками и о get_it не знают. Контейнер нужен только четырём тестам в `test/app/`.
- Состояние держит `flutter_bloc`, Cubit живёт столько, сколько экран (`BlocProvider` в маршруте).

То есть get_it здесь работает как композиционный корень, а не как локатор, который классы дёргают изнутри. Самая вредная форма антипаттерна в проекте отсутствует.

### Что плохо, и тут Дмитрий прав

1. **Один файл знает всё.** `di.dart` — 600 строк, 95 регистраций всех фич. Каждая новая фича правит его же, параллельные треды конфликтуют в одном месте. Связи между фичами не видны: любая регистрация может взять что угодно.
2. **Глобальное изменяемое состояние.** `GetIt.instance` — скрытая зависимость `router.dart` и `app.dart`; тесты обязаны вызывать `reset()`. `configureDependencies` принимает `locator`, но `bootstrap` и роутер всё равно ходят в глобальный.
3. **Ошибки только во время работы.** Забытая регистрация или опечатка в `instanceName` (`flossCatalogInstance`) — исключение при открытии экрана, а не ошибка компиляции. `di_test.dart` ловит часть случаев, но не все.
4. **Время жизни не совпадает с фичей.** `IsolateImageToGridRunner` нужен только мастеру «картинка → схема», но зарегистрирован синглтоном на всё приложение. Поэтому у него ручной `release()`: мастер обязан не забыть отпустить изолят. Так же живут `PdfRasterizer`, `BookImageSource`, `ImageDecoder`, `ImageMasks`, `OxsDecoder`, `DataTransferCubit`. Из-за ленивых синглтонов памяти тратится немного, но владельца у таких объектов нет.

Пункт 4 мельче, чем кажется: репозитории и так должны жить всё приложение (одна база, а синхронизация из ADR-0006 должна видеть изменения всех фич). Главные беды — 1, 2 и 3.

## Варианты

| Вариант | Что даёт | Чем плох здесь |
|---|---|---|
| Оставить как есть | Ноль работы | Пункты 1–4 остаются, синхронизация добавит ещё ~15 регистраций в тот же файл |
| get_it, но разбить на функции `registerXxx()` по фичам и `pushNewScope` для экранов | Мало работы | Глобальный контейнер и ошибки во время работы остаются; области get_it приходится вручную открывать и закрывать в маршрутах |
| `injectable` (генерация кода поверх get_it) | Меньше ручных регистраций | Ещё больше магии и `build_runner`, глобальный контейнер на месте |
| Riverpod | Современный, проверяемый граф, авто-освобождение | Заменяет flutter_bloc: переписать все Cubit, экраны и 212 тестов или жить с двумя подходами. Несоразмерно задаче |
| `RepositoryProvider`/`provider` в дереве виджетов | Уже есть в зависимостях (идёт с flutter_bloc) | Поиск по `context` — та же ошибка во время работы (`ProviderNotFound`), только в другом месте |
| **Модули фич на чистом Dart** (ручной DI, «Pure DI») | Граф проверяет компилятор, у каждой фичи свой файл и своё API, нет глобального состояния, нет пакета | Нужно один раз переписать `lib/app` (≈1200 строк) и 4 теста |

## Решение

Убираем get_it. Граф собирается обычным Dart-кодом из модулей фич, корень — один объект `AppDependencies`, который создаёт `bootstrap` и передаёт через конструкторы. Состояние по-прежнему держит flutter_bloc.

### Как выглядит модуль

```dart
/// lib/app/composition/weaving_module.dart
final class WeavingModule {
  WeavingModule({required CoreModule core, required GridModule grid, required ProjectsModule projects})
    : _core = core, _grid = grid, _projects = projects;

  final CoreModule _core;
  final GridModule _grid;
  final ProjectsModule _projects;

  // Живёт всё приложение, создаётся при первом обращении (замена registerLazySingleton).
  late final WorkSessionRepository sessions = DriftWorkSessionRepository(
    dao: _core.db.workSessionsDao,
    deviceIds: _core.deviceIds,
    clock: _core.clock,
    ids: _core.ids,
  );

  // Новый объект на каждый вызов (замена registerFactory / registerFactoryParam).
  WeaveCubit weaveCubit(String projectId) => WeaveCubit(
    projectId: projectId,
    projects: _projects.repository,
    patterns: _grid.patterns,
    tracker: WorkSessionTracker(sessions: sessions, clock: _core.clock),
    // ...
  );

  List<RouteBase> routes() => <RouteBase>[ /* маршруты плетения */ ];
}
```

Правила:

- **Модуль = фича.** Файлы в `lib/app/composition/`: `core_module.dart` (база, `Clock`, `IdGenerator`, `DeviceIdProvider`, `SettingsRepository`, `AppEvents`, `FileStore`, платформенные адаптеры), `projects_module.dart`, `grid_module.dart`, `weaving_module.dart`, `stitching_module.dart`, `book_module.dart`, `image_to_grid_module.dart`, `catalog_module.dart` (бисер и мулине), `sharing_module.dart`, `easter_eggs_module.dart`, `settings_module.dart`, позже `sync_module.dart`. Домен, данные и UI не меняются.
- **Связи явные.** Модуль получает в конструкторе только те модули, что ему нужны; наружу публично только то, что берут другие модули и маршруты, остальное приватное. Граф модулей ацикличен; где фичам нужно «собрать всех» (очистители и клонировщики содержимого для `DeleteProject`/`DuplicateProject`, пункты «Нового проекта»), список собирает `AppDependencies` и передаёт в `ProjectsModule`.
- **Три времени жизни, без отдельных механизмов:**
  - на всё приложение: `late final` поле модуля (репозитории, `AppEvents`, пасхалки, синхронизация);
  - на экран: метод модуля, который создаёт объект; владеет им `BlocProvider` маршрута, закрывает его вместе с экраном. Сюда уходят `ImageToGridRunner` (изолят живёт, пока открыт мастер, ручной `release()` больше не нужен как обязанность экрана), `PdfRasterizer`, `BookImageSource`, декодеры;
  - на вызов: use case создаётся внутри метода модуля, как сейчас `registerFactory`.
- **Освобождение.** У `AppDependencies` один `Future<void> dispose()`, который закрывает объекты приложения в обратном порядке (пасхалки, `AppEvents`, база). Сейчас это делает `getIt.reset()`.
- **Доступ из UI только через конструкторы.** `BeadingApp(dependencies)`, `createRouter(dependencies)`; маршруты фичи объявляет её модуль (`weaving.routes()`), `router.dart` их только складывает. Ни `InheritedWidget`, ни `context.read` для сервисов: поиск по дереву вернул бы ошибки во время работы. Исключение — то, что уже раздаётся через `BlocProvider` (тема, настройки).
- **Тесты.** `CoreModule` принимает необязательные подмены (`database`, `clock`, `catalogAssets`, платформенные адаптеры); `AppDependencies.create(core: ...)` собирает граф в тесте без глобального состояния, `reset()` не нужен. Тест композиции проверяет, что все маршруты строят свои Cubit (замена `di_test.dart`).
- **Пакет `get_it` удаляется** из `pubspec.yaml`; новое правило ревью: `lib/` не содержит глобальных контейнеров и `GetIt`.

### Почему так, а не «get_it по фичам»

Чистый Dart решает все четыре проблемы, а не две: компилятор проверяет граф, глобального объекта нет, у фичи свой файл и своё время жизни. Цена — одноразовая и локальная: меняется только `lib/app` и 4 теста, ни одна строка домена, данных и экранов не трогается, потому что они уже на конструкторах. Ручных регистраций не становится больше: вместо `..registerFactory<X>(() => X(container<A>(), container<B>()))` пишется `X x() => X(a, b)`. Riverpod был бы оправдан, если бы мы заодно меняли управление состоянием; этого никто не просил, и flutter_bloc нас устраивает.

## План миграции

Каждый шаг — отдельный PR в `dev`, зелёный `scripts/check.sh`, приложение работает после каждого шага. Пока идёт миграция, get_it и модули живут вместе: `di.dart` регистрирует объекты, взятые из модулей (`registerSingleton(core.clock)`), поэтому ещё не переведённые фичи ничего не замечают.

1. **Каркас и ядро.** `AppDependencies`, `CoreModule`; `bootstrap` создаёт `AppDependencies`, `di.dart` берёт ядро из него. Правило: новые фичи (синхронизация) — сразу модулем.
2. **Пасхалки и настройки** (`EasterEggsModule`, `SettingsModule`): `app.dart` получает зависимости через конструктор.
3. **Каталог и мулине** (`CatalogModule`): уходит именованная регистрация `flossCatalogInstance`.
4. **Сетка, плетение, вышивка, редактор** (`GridModule`, `WeavingModule`, `StitchingModule`), их маршруты переезжают в модули.
5. **Схемы из книги и мастер «картинка → схема»** (`BookModule`, `ImageToGridModule`): раннер изолята и растеризатор становятся объектами экрана.
6. **Обмен файлами и библиотека** (`SharingModule`, `ProjectsModule`, реестры «Нового проекта» и превью).
7. **Уборка.** Удалить `di.dart`, `getIt`, пакет `get_it`; `di_test.dart` → `composition_test.dart`; обновить `architecture.md`, `tasks.md` и правила ревью.

Шаги 2–6 независимы между собой, но правят `router.dart` и `di.dart`, поэтому идут по очереди, а не параллельно.

### Синхронизация (ADR-0006)

Тред синхронизации сейчас пишет домен и движок (T26) без DI. Чтобы не было встречного рефакторинга:

- до шага 1 вся проводка синхронизации живёт в отдельном файле `lib/app/composition/sync_wiring.dart` (одна функция), а не в `di.dart`; `getIt` в коде синхронизации вне этого файла не появляется;
- после шага 1 проводка становится `SyncModule(core: ..., projects: ...)`; `SyncEngine` и клиент Supabase — поля на всё приложение с `dispose` в `AppDependencies.dispose()`, экран входа получает Cubit через метод модуля.

## Последствия

- Плюсы: ошибка в графе — ошибка компиляции; у фичи свой файл и понятный список зависимостей; меньше конфликтов между тредами; у объектов экранов есть владелец; одной зависимостью меньше.
- Минусы: ручной код композиции нужно поддерживать (он и сейчас ручной); граф модулей придётся держать ацикличным; на время миграции два способа сосуществуют.
- Не меняются: домен, данные, экраны, Cubit, формат файлов, база, тесты фич.
